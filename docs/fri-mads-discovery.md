# Fri Mads read-only discovery

## Primary public source

The approved primary source is the publisher's public series overview: <https://frihedsbrevet.dk/nyhedsbrev/fri-mads/>. A bounded read-only check on 22 November 2026 followed the overview's own pagination across seven pages and found 171 numbered cards, continuously numbered from #172 through #2. The overview did not list #1, so it is not inferred. Only overview pages are read; article pages, paywalled text, images, and audio are never requested.

The public cards expose the exact `Fri Mads #N` heading, official permalink, byline, and Danish publication date. The parser accepts the observed colon, en-dash, and no-separator title forms, the exact `Fri Mads` category and official host, and numbered permalink URLs whose number matches the heading. Two observed historical cards (#6 and #3) have unnumbered legacy permalinks; only their exact verified URLs are allowlisted. Encoded Danish/Cyrillic/emoji permalink slugs are accepted after strict single-segment decoding. Unknown markup, missing byline/date, duplicate IDs, host/path conflicts, or gaps fail closed. Dates are emitted as calendar dates; no timezone or time is inferred.

The publisher RSS at <https://frihedsbrevet.dk/feed/> is a general feed of roughly ten recent articles across series, not a complete Fri Mads index. It is not fetched by the daily discovery because the approved overview already supplies the metadata needed. If RSS metadata is added later, it may supplement an overview card only after exact release-number and canonical-permalink equality; its repeated site-root GUID is never a release identity.

The stable identity is the exact series number plus its verified canonical permalink. There is no title fuzzy matching. The default `afterNumber=172` remains the initial cursor boundary. The one-time archive seed followed only official pagination links and was bounded to 12 pages/324 items; its verified result is the 171 cards #172–#2. The checked-in sidecar carries those verified records, not article bodies. Normal daily discovery still requests only the first page (a second page is allowed only if a future cursor boundary falls beyond that page). It stages only newly verified items and merges them with the existing sidecar after exact number/permalink checks, preserving historical rows without a daily archive scan. At most 27 new releases are returned per run. A boundary mismatch, number gap, changed permalink, or oversized window produces no update and a fixed review reason.

## Classification and limits

The existing catalogue identity remains `Podcast-ID=fri mads`, `catalogue_id=catalogue-v1-d94fc39e`, with the approved overview Link and historical article #140 in `accessEvidenceUrl`. Every discovered item is metadata-only paid article content: `contentKind=article`, `metadataOnly=true`, `playable=false`, `rateable=false`, `audioUrl=null`. No audio URL, duration, source GUID, or episode is invented. The adapter does not fetch article links, copy article text, or examine images/media.

The command `node scripts/discover-fri-mads-releases.mjs --dry-run` makes one bounded HTTPS GET in its normal path, with an 8-second timeout, redirects rejected, and a 512 KiB response cap. It makes a second bounded GET only for the documented incremental boundary condition. Reports contain allowlisted metadata/reason codes and state zero Supabase, Sheet, catalogue, or episode writes/imports. Network errors, raw response bodies, and arbitrary URLs are not logged.

The existing `episode-feed-coverage` workflow runs daily at 06:37 UTC and invokes this dry-run in that cadence; no new cron, storage, database access, or Supabase request was added. Identical source markup and cursor produce identical release IDs on repeated runs. The generic RSS is not used as primary discovery and no historical backfill is performed.

Discovery publishes only verified overview metadata through the existing trusted pull-request flow. The existing `fri_mads_official_articles` adapter maps each exact canonical article URL to a stable external identity and a normal importer UUID; it stores no article text, audio URL, duration, or image. These rows are eligible for the existing UUID-bound episode-rating model once the current Edge adapter version and sidecar are deployed and the normal importer cadence runs. It does not modify the catalogue, Sheet, existing episode rows, ratings, or the historical #140 access-evidence field. Any initial historical import must be preceded by an exact production dry-run and fresh episode/rating identity snapshots; no direct manual database write is part of discovery.

## Public article sidecar and profile list

`data/fri-mads-articles.json` contains the 171 records present in the approved official overview at the one-time seed check, #172 through #2. It stores only each exact series number, official title, calendar publication date, and canonical permalink, under the existing `fri mads` / `catalogue-v1-d94fc39e` identity and paid/article/metadata-only/non-playable classification. It contains no article text, image, audio URL, duration, episode ID, or rating data. The next daily workflow run reads only page 1 and preserves the older sidecar rows while appending new contiguous releases.

On the exact Fri Mads profile, the page requests this JSON through same-origin `data/fri-mads-articles.json` and merges each release into the podcast's ordinary episode workspace by its exact canonical permalink. A missing response, non-JSON response, invalid schema, duplicate identity, number gap, wrong host or malformed permalink leaves the verified article rows hidden and preserves the existing official series link. The normal episode table shows the official title, date, paid-access marker and the publisher link. It never fabricates an audio player, duration, or audio URL. Sidecar-only rows have no database UUID and therefore have no rating controls. After the existing importer stores the exact row under its stable UUID, that same episode row becomes rateable through the normal episode-rating flow; the sidecar entry is suppressed by URL identity so no duplicate appears.

The existing daily `episode-feed-coverage` workflow runs incremental discovery, then stages the sidecar only when metadata changes. It reuses `CATALOGUE_SYNC_PR_TOKEN` and the repository's existing trusted pull-request action, waits for the real `Critical Regression Gate` on the exact PR head, and requests auto-merge pinned to that SHA. A missing/invalid token or failed/stale gate stops publication. The workflow never writes directly to `main`; only `data/fri-mads-articles.json` is staged. Normal episode-import shards consume the sidecar on their existing 12-hour cadence after code and data are deployed. No new cron or database service is added.

The retained #173 test fixture is synthetic and remains isolated under `scripts/fixtures/`; it is absent from the published sidecar. Browser tests exercise the same-origin loader, invalid/missing data fallback, touch, keyboard focus, scrolling, overflow and responsive widths.
