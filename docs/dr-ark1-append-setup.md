# DR staging and owner-controlled Ark1 append gate

## Security model

GitHub Actions and its Workload Identity service account can write only to a separate, user-owned staging spreadsheet. The GitHub code contains no Sheets API client for the original spreadsheet, and no workflow secret or flag can enable a direct write to it. The staging writer is serialized by the existing catalogue workflow, validates the full staging schema and exact Podcast-ID, appends with `RAW`, never updates a row, and stops on ambiguous or duplicate identities.

The append into the original `Ark1` is a separate Apps Script bound to the original spreadsheet. The service account must not have any access to the original workbook. The owner reviews each proposed DR source in the original spreadsheet's `DR staging` menu and confirms it by typing the exact `APPEND <Podcast-ID>` phrase. The gate is disabled until the owner configures and verifies an independent backup and explicitly enables the script property. It takes a document lock, rechecks the target ID, tab name/gid and header, verifies unique existing IDs and source identity, appends only one new row, reads it back, and compares every pre-existing value and formula cell in `Ark1`. It has no update/delete/sort/clear path.

This owner-run bridge is intentionally manual. Google Sheets Editor permission is not technically append-only; the stronger boundary is that the GitHub service account has no permission on the original workbook and cannot invoke the owner-bound script as the owner. Do not install a time-driven trigger or enable unattended append until an independent security review explicitly approves that change.

## Source metadata for future DR series

The two existing editorial records remain tied to exact immutable Podcast-IDs and full DR episode URLs. For future discoveries, `dr-full-standalone-discovery.mjs` already records the official full-episode GUID, URL, title, and DR description when it can validate an active, sufficiently long full episode and an unambiguous route. The staging builder sanitizes that source text and can produce a short excerpt and bounded long description without inventing facts. It leaves host, genre, secondary genre, topics and similarities blank unless supplied by a verified source or existing curated metadata. Missing, teaser-only, malformed, conflicting, or incomplete provenance is never made append-eligible; the row is withheld or marked for editorial review. The owner sees the source URL/text and must review the entry before the Ark1 gate.

No additional polling job is introduced: the existing scheduled catalogue workflow reuses its current discovery and catalogue sync. Existing descriptions are preserved when discovery cannot verify replacement metadata.

## Owner setup (one time)

1. In the original Podcastlisten spreadsheet's sharing dialog, remove the `podcastlisten-sheets-writer@podcastlisten-automation.iam.gserviceaccount.com` account or set it to Viewer. Also remove any other automation identity that was granted Editor for the old direct-append implementation. Do not proceed until no GitHub service account can edit the original.
2. In a user-owned Drive location, create a separate Google spreadsheet for DR staging with a tab named exactly `DR staging`. Put the exact staging header schema in row 1: the existing Ark1 columns (including column T `Supplerende ligheder`, and all trailing blank/header columns) followed by `DR source GUID`, `DR source URL`, `DR source description`, `Review status`. Keep owner-only backup and gate configuration separate from this staging file.
3. In a separate Google Cloud project, enable Google Sheets API. Use a dedicated service account with no project/Workspace admin role, no domain-wide delegation and no JSON key. Share only the staging spreadsheet with that account as Editor. Do not share the original spreadsheet with it.
4. Configure Workload Identity Federation for this repository and protected `main`. Limit the provider condition to the exact repository and this trusted workflow (`vm2026-manager/podcast-ratings/.github/workflows/sync-sheet-data.yml@refs/heads/main` via the `workflow_ref` claim), and allow only the dedicated staging service account to be impersonated. Do not grant OIDC to pull request workflows. GitHub Actions uses short-lived tokens scoped to Sheets; it receives no Drive or original-sheet authority.
5. Set GitHub Actions variables `GOOGLE_WORKLOAD_IDENTITY_PROVIDER`, `GOOGLE_DR_STAGING_SERVICE_ACCOUNT`, `GOOGLE_DR_STAGING_SHEET_ID` (the separate staging spreadsheet ID), and `GOOGLE_DR_STAGING_WRITE_ENABLED`. Leave the last variable unset/`false` until read-only staging dry-run and security checks pass. The old `GOOGLE_SHEETS_SPREADSHEET_ID`, `GOOGLE_SHEETS_WRITE_ENABLED`, and `GOOGLE_SHEETS_BACKUP_VERIFIED` are not used and must not be re-enabled.
6. Before first append, make a versioned, full independent copy of the entire original spreadsheet in a location inaccessible to the service account, staging workflow **and Apps Script**. Verify every tab and data range in a restored test copy. Do not rely on protected ranges or version history alone. Before **each** owner-run append, make a fresh full copy in that independent location.
7. From the original workbook, create a bound Apps Script project and copy `apps-script/append-dr-staging-to-ark1/Code.gs` into it. Review the code and compare the original spreadsheet ID and tab ID (`Ark1`, gid 0). The owner sets these Script Properties: `OWNER_EMAIL` (owner's exact Google account), `STAGING_SPREADSHEET_ID`, `BACKUP_SPREADSHEET_ID` (reference only; the script never opens the backup), `BACKUP_VERIFIED_AT` (current ISO timestamp, refreshed for every append), `BACKUP_RESTORE_TEST_VERIFIED=true`, and only after explicit approval `APPEND_ENABLED=true`. Keep it `false` by default. The script compares existing Ark1 cell values and formulas immediately before and after each append; it cannot access the independent backup. The owner attestation records that a full restore was tested on a separate test copy; the script never restores production.
8. The owner opens/reloads the original sheet, uses **DR staging → Gennemgå og tilføj verificerede serier**, checks the official DR source and proposed row, then types `APPEND <Podcast-ID>` for each approved candidate. This is the only implemented bridge from staging to original. The next ordinary catalogue sync reads the original published CSV and honors any editor changes as the source of truth.

## Tests and activation boundary

Mock tests cover staging append/rerun, preserve existing staging edits, duplicate/header/source failures, formula-like payloads, ambiguous timeout recovery and serialized workflow. Apps Script tests mock the original/staging workbooks, lock, owner checks, backup gates, wrong gid/header, duplicate IDs, manual approval, existing-cell/formula integrity, append timeout, and parallel execution. Tests never authenticate to Google or mutate production. Production activation remains disabled until the owner has completed the Cloud, sharing, backup and Apps Script setup above and independently reviewed the results.
