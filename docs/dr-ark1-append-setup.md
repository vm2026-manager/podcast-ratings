# DR staging and owner-controlled Ark1 append gate

## Security model

GitHub Actions and its Workload Identity service account can write only to a separate, user-owned staging spreadsheet. The GitHub code contains no Sheets API client for the original spreadsheet, and no workflow secret or flag can enable a direct write to it. The staging writer is serialized by the existing catalogue workflow, validates the full staging schema and exact Podcast-ID, appends with `RAW`, and stops on ambiguous or duplicate identities. The integrated workflow runs in append-only mode: it never changes an existing staging row or cell, including blank host cells.

The append into the original `Ark1` is a separate Apps Script bound to the original spreadsheet. The service account must not have any access to the original workbook. The owner reviews each proposed DR source in the original spreadsheet's `DR staging` menu and confirms it by typing the exact `APPEND <Podcast-ID>` phrase. Radio IIII uses a separate `Radio IIII staging` menu and also requires a per-candidate `GENRE Samfund <Podcast-ID>` approval before the exact append phrase. The gate is disabled until the owner configures and verifies an independent backup and explicitly enables the script property. It takes a document lock, rechecks the target ID, tab name/gid and header, verifies unique existing IDs and source identity, appends only one new row, reads it back, and compares every pre-existing value and formula cell in `Ark1`. It has no update/delete/sort/clear path.

This owner-run bridge is intentionally manual. Google Sheets Editor permission is not technically append-only; the stronger boundary is that the GitHub service account has no permission on the original workbook and cannot invoke the owner-bound script as the owner. Do not install a time-driven trigger or enable unattended append until an independent security review explicitly approves that change.

Tyran proposals reuse the same `DR staging` tab and exact existing headers. The scheduled staging workflow reads `data/auto-discovered-tyran.json`, validates the immutable Macias and Marcos identities against their DR series pages, first full episodes, individual 720×720 covers and SHA-256 checksums, then stages only Macias. Marcos is the existing Ark1 Podcast-ID `marcos`; it is validated and skipped. The 22 protected historical Tyran identities remain protected. Provenance is carried in the existing `DR source description` field so no staging columns or workflow jobs are added. Every proposal stays `NEEDS_EDITORIAL_REVIEW`; episode feeds, ratings and history remain blank.

The current staging sheet contains two one-cell notes reading `Macias` in the DR source GUID column. Neither has a Podcast-ID or other identity fields. The workflow reports and preserves both unchanged; any orphan row containing a title, main series, URL, or numeric GUID remains a hard stop for manual review. DR proposals are written to an explicit row after the last populated row, then checked across all columns. The Sheets append endpoint is not used because a lone provenance-column note can make its table detection choose the wrong target.

The Apps Script has a separate **DR staging → Gennemgå Tyran-forslag (ejerstyret)** action. It is read-only by default: the owner can run the source, collision and schema dry run while `TYRAN_APPEND_ENABLED` is unset/`false`; the action then reports that appends remain closed. It does not install or activate this code. An owner who later elects to append must review the latest code, enable the existing owner gate and set `TYRAN_APPEND_ENABLED=true` deliberately, make an independent full backup and verify a test restore within 15 minutes of the individual append, rerun the menu, and type the exact `APPEND tyran-auto-v1-08d0021f` phrase for Macias. The script re-reads the candidate and Ark1 under a document lock, checks the complete old-sheet snapshot, appends one row and verifies every written cell by readback. Marcos and any matching title, source, episode GUID, series ID, production number, cover or protected historical identity are never appended as a duplicate. Leave the Tyran property unset/`false` unless the owner has completed those steps and decided to transfer the row.

## Source metadata for future DR series

Verified DR metadata records remain tied to exact immutable Podcast-IDs and full DR episode URLs. The existing legacy identity `dræberurten` is bound to the official full episode `16122692641` and remains marked for owner review. For future discoveries, `dr-full-standalone-discovery.mjs` records the official full-episode GUID, URL, title, and DR description when it can validate an active, sufficiently long full episode and an unambiguous route. It extracts a host only from an explicit DR credit label containing “vært”, including combined roles such as “Tilrettelæggelse, vært og lyddesign”. Guest, contributor, producer, editor and organizer credits do not qualify by themselves. Conflicting or absent host credits leave the field blank and require editorial review; umbrella-show hosts are never copied to child series. The staging builder sanitizes source text and can produce a short excerpt and bounded long description without inventing facts. Secondary genre, episode count, topics and similarities remain blank unless supplied by verified source or curated metadata. Missing, teaser-only, malformed, conflicting, or incomplete provenance is never made append-eligible; the row is withheld or marked for editorial review. The owner sees the exact source URL/text and proposed host and must review the entry before the Ark1 gate. Apps Script accepts a nonempty host only when the source text contains a matching explicit host credit or a built-in exact Podcast-ID/GUID/URL credit match; the owner still types the exact `APPEND <Podcast-ID>` phrase for each row.

No additional polling job is introduced: the existing scheduled catalogue workflow reuses its current discovery and catalogue sync. Existing descriptions are preserved when discovery cannot verify replacement metadata.

## Owner setup (one time)

1. In the original Podcastlisten spreadsheet's sharing dialog, remove the `podcastlisten-sheets-writer@podcastlisten-automation.iam.gserviceaccount.com` account or set it to Viewer. Also remove any other automation identity that was granted Editor for the old direct-append implementation. Do not proceed until no GitHub service account can edit the original.
2. In a user-owned Drive location, create a separate Google spreadsheet for DR staging with a tab named exactly `DR staging`. Put the exact staging header schema in row 1: the existing Ark1 columns (including column T `Supplerende ligheder`, and all trailing blank/header columns) followed by `DR source GUID`, `DR source URL`, `DR source description`, `Review status`. Keep owner-only backup and gate configuration separate from this staging file.
3. In a separate Google Cloud project, enable Google Sheets API. Use a dedicated service account with no project/Workspace admin role, no domain-wide delegation and no JSON key. Share only the staging spreadsheet with that account as Editor. Do not share the original spreadsheet with it.
4. Configure Workload Identity Federation for this repository and protected `main`. Limit the provider condition to the exact repository and this trusted workflow (`vm2026-manager/podcast-ratings/.github/workflows/sync-sheet-data.yml@refs/heads/main` via the `workflow_ref` claim), and allow only the dedicated staging service account to be impersonated. Do not grant OIDC to pull request workflows. GitHub Actions uses short-lived tokens scoped to Sheets; it receives no Drive or original-sheet authority.
5. Set GitHub Actions variables `GOOGLE_WORKLOAD_IDENTITY_PROVIDER`, `GOOGLE_DR_STAGING_SERVICE_ACCOUNT`, `GOOGLE_DR_STAGING_SHEET_ID` (the separate staging spreadsheet ID), and `GOOGLE_DR_STAGING_WRITE_ENABLED`. Leave the last variable unset/`false` until read-only staging dry-run and security checks pass. The old `GOOGLE_SHEETS_SPREADSHEET_ID`, `GOOGLE_SHEETS_WRITE_ENABLED`, and `GOOGLE_SHEETS_BACKUP_VERIFIED` are not used and must not be re-enabled.
6. Before first append, make a versioned, full independent copy of the entire original spreadsheet in a location inaccessible to the service account, staging workflow **and Apps Script**. Verify every tab and data range in a restored test copy. Do not rely on protected ranges or version history alone. Before **each individual owner-run append**, make a fresh full copy in that independent location and verify a test restoration of that copy. Refresh `BACKUP_VERIFIED_AT` only after both the new copy and its test restoration are complete. The Radio IIII gate requires this attestation to be no more than 15 minutes old immediately before its one-row append; run the menu separately for each guest.
7. From the original workbook, create a bound Apps Script project and copy `apps-script/append-dr-staging-to-ark1/Code.gs` into it. Review the code and compare the original spreadsheet ID and tab ID (`Ark1`, gid 0). The owner sets these Script Properties: `OWNER_EMAIL` (owner's exact Google account), `STAGING_SPREADSHEET_ID`, `BACKUP_SPREADSHEET_ID` (reference only; the script never opens the backup), `BACKUP_VERIFIED_AT` (current ISO timestamp, refreshed for every append), `BACKUP_RESTORE_TEST_VERIFIED=true`, and only after explicit approval `APPEND_ENABLED=true`. Keep it `false` by default. The script compares existing Ark1 cell values and formulas immediately before and after each append; it cannot access the independent backup. The owner attestation records that a full restore was tested on a separate test copy; the script never restores production.
8. For existing Bakspejl/Djævlen proposals, the owner opens/reloads the original sheet, uses **DR staging → Gennemgå og tilføj verificerede serier**, checks the official DR source and proposed row, then types `APPEND <Podcast-ID>` for the single approved candidate. For Tyran, first run the separate Tyran action with the append property closed; it performs a read-only dry run. Only if the owner elects to transfer Macias, follow the fresh-backup and explicit property steps above, rerun the Tyran action, inspect the series and episode sources plus cover checksum, then type the exact ID phrase. No owner action or staging job appends Marcos because Ark1 already contains that identity. The next ordinary catalogue sync reads the original published CSV and honors any editor changes as the source of truth.
9. To install Radio IIII owner review, copy the reviewed `apps-script/append-dr-staging-to-ark1/Code.gs` from the merged repository into the owner-bound Apps Script project and reload the workbook. The separate **Radio IIII staging → Gennemgå og tilføj verificeret gæsteserie** action reads only A:AJ (36 columns) from that tab. It validates the four immutable Podcast-IDs against the official chapter URL, season URL and ordered set of five GUIDs, then checks Ark1 IDs, titles, source URLs and GUID collisions. It refuses the staging genre `Portræt` as an Ark1 genre because it is not an active catalogue genre. For each candidate separately, the owner must approve the proposed active genre by typing `GENRE Samfund <Podcast-ID>`, then approve one new row by typing `APPEND <Podcast-ID>`. `Samfund` is the editorial proposal; the script does not change the staging cell. The appended row has empty placement, score, rating date, listening history, secondary genre, feed, similarity, stale, access and English fields. No existing row is updated.

## Tests and activation boundary

Mock tests cover staging append/rerun, blank-host-only fill, preservation of existing staging edits, duplicate/header/source failures, formula-like payloads, ambiguous timeout recovery and serialized workflow. Apps Script tests mock the original/staging workbooks, lock, owner checks, backup gates, wrong gid/header, duplicate IDs, manual approval, explicit host-credit validation, existing-cell/formula integrity, append timeout, and parallel execution. Radio IIII tests additionally cover all four immutable guest IDs, A:AJ-only reads, exact season/GUID/source checks, inactive-genre refusal and explicit per-ID genre approval, identity collisions, fresh backup per append, idempotency and preservation of the 60 existing guest rows. Tests never authenticate to Google or mutate production. Production activation remains disabled until the owner has completed the Cloud, sharing, backup and Apps Script setup above and independently reviewed the results.
