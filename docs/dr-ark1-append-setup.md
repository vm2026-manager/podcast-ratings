# DR staging and owner-controlled Ark1 append gate

## Security model

GitHub Actions and its Workload Identity service account can write only to a separate, user-owned staging spreadsheet. The GitHub code contains no Sheets API client for the original spreadsheet, and no workflow secret or flag can enable a direct write to it. The staging writer is serialized by the existing catalogue workflow, validates the full staging schema and exact Podcast-ID, appends with `RAW`, and stops on ambiguous or duplicate identities. The integrated workflow runs in append-only mode: it never changes an existing staging row or cell, including blank host cells.

The append into the original `Ark1` is a separate Apps Script bound to the original spreadsheet. The service account must not have any access to the original workbook. The new **Ejerstyret staging → Gennemgå stagingforslag samlet** action reads `DR staging` and `Radio IIII staging`, presents one read-only overview across Bakspejl, Djævlen i detaljen, Tyran and Et kapitel for sig, and accepts one exact owner confirmation for the full validated batch. Only `SOURCE_VERIFIED_REQUIRES_OWNER_APPROVAL` and individually reviewed `EDITORIALLY_APPROVED_SOURCE_VERIFIED` rows are eligible. `NEEDS_EDITORIAL_REVIEW` rows are displayed with their missing evidence and excluded. Radio IIII uses the owner-approved genre `Samfund` only on the new Ark1 rows; staging remains unchanged. One independent full backup and verified test restore is required for the batch, not for each row. The gate takes one document lock for the batch, rechecks target IDs, tab/gid and schema, checks source/GUID/cover collisions before the first write, reads every added row back, and compares every pre-existing value and formula cell in `Ark1`. It closes `APPEND_ENABLED` automatically after success, cancellation or failure and has no update/delete/sort/clear path.

This owner-run bridge is intentionally manual. Google Sheets Editor permission is not technically append-only; the stronger boundary is that the GitHub service account has no permission on the original workbook and cannot invoke the owner-bound script as the owner. Do not install a time-driven trigger or enable unattended append until an independent security review explicitly approves that change.

Tyran proposals reuse the same `DR staging` tab and exact existing headers. The scheduled staging workflow reads `data/auto-discovered-tyran.json`, validates the immutable Macias and Marcos identities against their DR series pages, first full episodes, individual 720×720 covers and SHA-256 checksums, then stages only Macias. Marcos is the existing Ark1 Podcast-ID `marcos`; it is validated and skipped. The 22 protected historical Tyran identities remain protected. Provenance is carried in the existing `DR source description` field so no staging columns or workflow jobs are added. Proposals remain `NEEDS_EDITORIAL_REVIEW` until an owner completes an individual editorial review and source verification, fills the required host, active genre and topics, and changes the review status to `EDITORIALLY_APPROVED_SOURCE_VERIFIED`. Episode feeds, ratings and history remain blank.

The current staging sheet contains two one-cell notes reading `Macias` in the DR source GUID column. Neither has a Podcast-ID or other identity fields. The workflow reports and preserves both unchanged; any orphan row containing a title, main series, URL, or numeric GUID remains a hard stop for manual review. DR proposals are written to an explicit row after the last populated row, then checked across all columns. The Sheets append endpoint is not used because a lone provenance-column note can make its table detection choose the wrong target.

The legacy **DR staging → Gennemgå Tyran-forslag (ejerstyret)** action remains available. The shared batch gate excludes Tyran rows until individual editorial review and official source evidence are recorded with the status `EDITORIALLY_APPROVED_SOURCE_VERIFIED`; it then checks structured provenance and the source-description digest before treating the row as eligible. Marcos and any matching title, source, episode GUID, series ID, production number, cover or protected historical identity are never appended as a duplicate. The Apps Script is not installed or activated by this repository change.

## Source metadata for future DR series

Verified DR metadata records remain tied to exact immutable Podcast-IDs and full DR episode URLs. The existing legacy identity `dræberurten` is bound to the official full episode `16122692641` and remains marked for owner review. For future discoveries, `dr-full-standalone-discovery.mjs` records the official full-episode GUID, URL, title, and DR description when it can validate an active, sufficiently long full episode and an unambiguous route. It extracts a host only from an explicit DR credit label containing “vært”, including combined roles such as “Tilrettelæggelse, vært og lyddesign”. Guest, contributor, producer, editor and organizer credits do not qualify by themselves. Conflicting or absent host credits leave the field blank and require editorial review; umbrella-show hosts are never copied to child series. The staging builder sanitizes source text and can produce a short excerpt and bounded long description without inventing facts. Secondary genre, episode count, topics and similarities remain blank unless supplied by verified source or curated metadata. Missing, teaser-only, malformed, conflicting, or incomplete provenance is never made append-eligible; the row is withheld or marked for editorial review. The owner sees the exact source URL/text and proposed host and must review the entry before the Ark1 gate. Apps Script accepts a nonempty host only when the source text contains a matching explicit host credit or a built-in exact Podcast-ID/GUID/URL credit match; the owner still types the exact `APPEND <Podcast-ID>` phrase for each row.

No additional polling job is introduced: the existing scheduled catalogue workflow reuses its current discovery and catalogue sync. Existing descriptions are preserved when discovery cannot verify replacement metadata.

## Owner setup (one time)

1. In the original Podcastlisten spreadsheet's sharing dialog, remove the `podcastlisten-sheets-writer@podcastlisten-automation.iam.gserviceaccount.com` account or set it to Viewer. Also remove any other automation identity that was granted Editor for the old direct-append implementation. Do not proceed until no GitHub service account can edit the original.
2. In a user-owned Drive location, create a separate Google spreadsheet for DR staging with a tab named exactly `DR staging`. Put the exact staging header schema in row 1: the existing Ark1 columns (including column T `Supplerende ligheder`, and all trailing blank/header columns) followed by `DR source GUID`, `DR source URL`, `DR source description`, `Review status`. Keep owner-only backup and gate configuration separate from this staging file.
3. In a separate Google Cloud project, enable Google Sheets API. Use a dedicated service account with no project/Workspace admin role, no domain-wide delegation and no JSON key. Share only the staging spreadsheet with that account as Editor. Do not share the original spreadsheet with it.
4. Configure Workload Identity Federation for this repository and protected `main`. Limit the provider condition to the exact repository and this trusted workflow (`vm2026-manager/podcast-ratings/.github/workflows/sync-sheet-data.yml@refs/heads/main` via the `workflow_ref` claim), and allow only the dedicated staging service account to be impersonated. Do not grant OIDC to pull request workflows. GitHub Actions uses short-lived tokens scoped to Sheets; it receives no Drive or original-sheet authority.
5. Set GitHub Actions variables `GOOGLE_WORKLOAD_IDENTITY_PROVIDER`, `GOOGLE_DR_STAGING_SERVICE_ACCOUNT`, `GOOGLE_DR_STAGING_SHEET_ID` (the separate staging spreadsheet ID), and `GOOGLE_DR_STAGING_WRITE_ENABLED`. Leave the last variable unset/`false` until read-only staging dry-run and security checks pass. The old `GOOGLE_SHEETS_SPREADSHEET_ID`, `GOOGLE_SHEETS_WRITE_ENABLED`, and `GOOGLE_SHEETS_BACKUP_VERIFIED` are not used and must not be re-enabled.
6. Before a batch, make one fresh, versioned full independent copy of the entire original spreadsheet in a location inaccessible to the service account, staging workflow **and Apps Script**. Verify every tab and data range in a restored test copy. Do not rely on protected ranges or version history alone. Refresh `BACKUP_VERIFIED_AT` only after the copy and test restoration are complete; the batch requires the attestation to be no more than 15 minutes old.
7. In the original workbook's existing bound Apps Script project, replace `Code.gs` with `apps-script/append-dr-staging-to-ark1/Code.gs` from the reviewed repository version (create a bound project only if none exists). Review the code and compare the original spreadsheet ID and tab ID (`Ark1`, gid 0). Set `OWNER_EMAIL`, `STAGING_SPREADSHEET_ID`, `BACKUP_SPREADSHEET_ID` (reference only; the script never opens the backup), `BACKUP_VERIFIED_AT`, and `BACKUP_RESTORE_TEST_VERIFIED=true`. Leave `APPEND_ENABLED=false` until the verified backup and complete batch review are ready. Set it to `true` once for that batch; the script closes it automatically after the attempt. It compares existing Ark1 cell values and formulas before and after writes; it cannot access the independent backup or restore production.
8. Reload the original workbook and choose **Ejerstyret staging → Gennemgå stagingforslag samlet**. Review the single overview of all validated DR and Radio IIII proposals, their exact IDs, sources, covers, genres, statuses, and the already-present Mattias Tesfaye and Marcos identities. Dræberurten and Macias stay excluded until individually reviewed and source-verified. If the full set and backup are correct, enter the exact batch phrase shown in the dialog once. The older DR, Tyran and Radio IIII menu items remain available for their existing owner-run workflows. The next ordinary catalogue sync reads the original published CSV and honors any editor changes as the source of truth.

## Tests and activation boundary

Mock tests cover staging append/rerun, blank-host-only fill, preservation of existing staging edits and Macias notes, duplicate/header/source/GUID/cover failures, formula-like payloads, ambiguous timeout recovery, editorial-review gates and serialized workflows. The shared Apps Script tests cover one aggregate confirmation and backup, dynamic guests from all four series, protected Mattias and Marcos identities, document locking, target/staging snapshots, partial-write reporting, idempotency, automatic gate closure, and unchanged ratings/history. Radio IIII tests additionally cover all four immutable guest identities, A:AJ-only reads, exact season/GUID/source/cover checks, inactive-genre refusal and the preserved legacy menu. Tests never authenticate to Google or mutate production. Production activation remains disabled until the owner has completed the Cloud, sharing, backup and Apps Script setup above and independently reviewed the results.
